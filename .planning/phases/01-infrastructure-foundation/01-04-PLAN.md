<objective>
Close Phase 1 by proving the platform is reproducible, resource-safe, and reachable from Python — the three things Phase 2 assumes and none of which are proven by "the containers are running".

Purpose: three failure modes survive everything the previous plans verified. First, the stack may only work on the machine that built it incrementally — plans 01-01 through 01-03 each added services to an already-warm stack, and a cold start from teardown exercises startup ordering and healthcheck dependencies that an incremental build never did (INFRA-01). Second, memory may be over-committed in a way that only manifests under load — Pitfall 9 records ClickHouse exiting 137 when the OTel demo's full mode crowds it out, and Phase 4 deliberately injects load on top of this baseline, so unmeasured headroom means the demo dies mid-presentation (INFRA-05). Third, the services being reachable over curl does not prove the Python client libraries connect — the numpy<2.0 / GQLAlchemy constraint, the Bolt handshake against Memgraph 3.x, and the ClickHouse driver against the real SigNoz schema are each an independent failure point that Phase 2 would otherwise discover with its own budget.

This plan also settles the Claude's-Discretion item on verification tooling: a Python script rather than a shell script, because the checks that matter most are exactly the ones that must run through the Python client stack.

Output: `scripts/verify_stack.py` (the single Phase 1 gate), `docs/RESOURCE_BASELINE.md` (measured memory against the 14GB budget), and `README.md` (the cold-start runbook).
</objective>

<verification_scope_contract>
`scripts/verify_stack.py` is the single command that answers "is Phase 1 still green?". It is run at
the end of this plan, at the start of Phase 2, and before the Phase 5 demo. It must therefore:

  - be READ-ONLY against every service except Memgraph's own persistence probe node. It must never
    drop a collection, truncate a table, or delete a node. Phase 2 will seed real data into these
    same services and re-running this script must never destroy it.
  - exit 0 only if every check passes; exit non-zero on the first hard failure category, after
    running and reporting ALL checks. Fail-fast on the first check would hide the other nine.
  - print one line per check in a fixed `PASS|FAIL  <check-id>  <detail>` shape so the output is
    greppable, and a final summary count.
  - read its expected values from the committed docs (`docs/PORTS.md`, `docs/CLICKHOUSE_SCHEMA.md`,
    `docs/OTEL_DEMO_SERVICES.md`) or from module-level constants that name those docs as the source
    — never from hardcoded values that silently drift from the ledger.
  - take zero arguments for the default run. Optional flags are fine; the zero-argument invocation
    must be the full gate.
</verification_scope_contract>

separate reported check with a stable id:

  GRAPH-03 the PersistenceProbe node written in plan 01-01 is still present (named volume intact, D-06)
  VEC-01   qdrant-client connects and lists collections without error
  TELE-01  clickhouse-connect connects and the resolved signoz_logs table from
           docs/CLICKHOUSE_SCHEMA.md exists
  TELE-02  the resolved logs table has rows within a recent window
  TELE-03  the resolved traces table has more than one distinct service within a recent window
  SVC-01   the distinct service-name set in recent telemetry covers every service listed in
           docs/OTEL_DEMO_SERVICES.md, and specifically the payment, checkout, and frontend services

  UI-01    HTTP 200 from 127.0.0.1:3301 (SigNoz), 127.0.0.1:3000 (Memgraph Lab), 127.0.0.1:8090 (storefront)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verification script -> all three data planes | The script holds credentials and connects to every service; it is the one component with reach across all planes. |
| README instructions -> operator behaviour | Documented commands are executed verbatim; a wrong teardown command destroys data. |
| host resource pool -> all containers | Containers compete for a fixed memory allocation; one greedy container can evict another. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-24 | Denial of service | Memory over-commit causing ClickHouse OOM (exit 137) mid-demo | mitigate | Measured 10-minute steady-state baseline with the load generator active, per-container table, explicit headroom verdict, and acceptance criteria asserting `State.OOMKilled` is false and no exit code is 137 for every container. This converts Pitfall 9 from an estimate into a measured figure with a named trim list. |
